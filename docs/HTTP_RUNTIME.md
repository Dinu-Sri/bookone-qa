## Fixtures and evidence boundaries

Each database-role lane starts a fresh guarded fixture after the previous Next process has exited. The seeder uses actual product invoice/payment/credential-creation helpers with the declared synthetic-session adapter ONLY during fixture preparation. It creates six synthetic identities: Owner, assigned Viewer, foreign Owner, platform Admin, legacy Viewer without a primary job and legacy Owner without a primary job. The compiled Next application uses the real auth/session/request modules with no Vitest aliases. Credentials, cookies, TLS keys, records and raw logs remain private in ignored .local/http/.

The original runtime fixtures explicitly pre-enable modules; this HTTP lane does not certify signup/Add company defaults. BUG-0050/RT-062 remains independently red. Owner-DB functional baseline and the actual non-owner NOSUPERUSER/NOBYPASSRLS app role are separate boundaries, not new business workflows. Role metadata is probed before launch. The shared fixture is reset only between stopped processes in the verified ephemeral database; never company-reset SQL against staging.

Read-only identity diagnostics probe known synthetic users using the exact app DB role before launch: unscoped visibility, transaction-local correct-tenant visibility, foreign visibility and visibility after transaction completion. The GUC applies only to that separate short-lived probe connection and is rolled back at transaction end; it is never injected into the running app. These probes explain an ERP identity failure but cannot make its blocked cases pass. Anonymous redirect diagnostics publish only fixed numeric origin/path categories. A known-foreign invoice may redirect to the same-origin invoice list by the pinned route contract; only that case explicitly allows that fallback, retaining known-own positives, foreign-data absence and unchanged-state assertions. Off-origin redirects are still failed and never followed.

Manifest batches/http-runtime.json retains nine assertions per role boundary (18 slots): real login/secure cookies/anonymous and invalid-password controls; actual session plus loaded Owner/Viewer/foreign role and own invoice; known existing foreign record denial; rendered profile Server Action Viewer denial and Owner persisted positive; normal-role Control Room denial/platform Admin positive; logout and stale cookie replay; existing receipt150 real server rendering with no posting; actual financial action Viewer/foreign denial and Owner25 exact journal/subledger; legacy Viewer must not become Owner on session loading, with legacy Owner repair/payment positive.

Real action response status alone never proves a write or rejection; independent persisted business snapshots and exact amount/account/actor/date checks are required. Financial requests are sent once, with fresh UUID idempotency keys; ambiguous outcomes are not replayed. Final private snapshots and allowlisted numeric balances are retained before the isolated next-lane reset.

The public summary includes exact product/QA/content/lock/Next build/version fingerprints, fixed case IDs, counts, allowlisted assertion/category labels and numeric synthetic observations. No raw exception/SQL/response/URL/identity passthrough. Setup failures block every unexecuted required case. Passed/failed/blocked remain distinct; missing prerequisites cannot pass.
