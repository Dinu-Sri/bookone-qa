# Isolated PostgreSQL layer

Current product baseline is deliberately pinned in product-ref.json; v2.2.4/343d546 is the latest reviewed candidate. PostgreSQL driver3.4.9, Drizzle0.33.0 and drizzle-kit0.24.2 match its lockfile. This lane is independent of the embedded PGlite source contracts and never connects to shared staging.

CI service is bound to127.0.0.1 on its disposable runner, with trust authentication only for that isolated service. The URL and restricted-role password are generated per run and masked/private; no fixed password is committed. Real database role/RLS and permissions are tested, not PostgreSQL password authentication. Actual deployed credentials/connection authentication remain unverified. Never copy this service configuration into shared staging or production.

CI provisions a fresh PostgreSQL16 service with a dedicated database. Locally, provide `QA_RUNTIME_ADMIN_URL` for an empty loopback database named `bookone_qa_runtime`, and `QA_RUNTIME_ISOLATION=ephemeral-local-postgres`; then `pnpm product:prepare`, `pnpm runtime:prepare`, `pnpm runtime:run`. No local PostgreSQL tools were available when this was written; CI is the execution route. There is no unattended live replay or database reuse. Generate a fresh service for every run.

Preparation verifies the product pin, refuses nonempty databases, pushes the complete current product Drizzle schema, applies every ordered SQL migration without catch-and-ignore, records migration hashes/results privately, and creates a random-password non-owner NOBYPASSRLS role. Failed preparation remains failed; no skipped migration is called applied. This checks the current schema-plus-SQL fresh setup path, not historical upgrades, product startup swallowing, registration, or backup restore.

The RLS lane uses the actual product db.ts/helpers.ts and postgres-js connection pool with that restricted role. RT-001 independently verifies role flags, table RLS and positive own/foreign fixtures using an explicitly bound transaction. RT-002 checks that the product tenant helper retains its context in the callback. RT-003 exercises a separate connection and foreign read/write denial. RT-004 checks alternating tenant callbacks and clearing after an exception. An isolated helper failure does not prove the deployed app leaks data; production connection role/reachability remains unverified.

The commercial lane uses an owner connection to separate business action correctness from tenant-helper failures. This matches a permissive DB-owner mode but does not establish safe RLS. Authenticated identity is synthetic; memberships/templates/overrides and permission loading, dimensions, actual commercial creation/posting, payments, SQL/FK/unique constraints, journals and audits use pinned product code. Next cache/navigation/headers and the server-only bundler sentinel are narrow adapters. There is no credential login or HTTP server in this lane.

Initial cases: B-101 quote/order/draft persisted links and no financial/stock posting; B-102 actual service/digital draft-to-post with exact Dr1300/Cr4000 amount600 and unchanged stock; B-103 actual invoice followed by receipt250/350 with balances/journals/audit at each transition; E-115 persisted Owner/Sales positive versus Viewer deny; E-116 module/entity ceilings; E-117 override boundaries. These implement portions of the lifecycle specifications; print/browser, wider jobs/scopes/settings and object storage remain open.

The added reversal lane uses an owner connection, actual Simple Entry sale and reversal, real persisted permission loading and multiple PostgreSQL connections. RT-005 checks exact sequential offset/links/audit and duplicate denial; RT-007 checks Viewer denial against an existing sale. RT-006 overlaps two action requests and introduces a250ms insert delay only in the isolated fixture to widen contention after preflight reads. It changes no money/locking/return values and is removed in finally. This is a targeted contention experiment, not deployed HTTP concurrency or safe non-owner runtime acceptance. Product failures remain red. A later pin must satisfy the unchanged single-reversal invariant with adjacent outcomes, not merely hide the timing window.

`runtime:run` verifies preparation/pin and records exact expected cases. Missing/duplicate/skipped/setup-failed cases and subprocess errors fail closed. Independent lanes continue after a product failure. It stores raw logs, connection URL and checkpoints only under ignored `.local/runtime`; public summaries contain only IDs/statuses and a revision/content/schema fingerprint. Summaries are immutable and do not constitute release approval. No automatic resume into a mutated database: create a new fixture and run after any source/test/dependency change. Review failure sensitivity before using these assertions as a promotion gate.
