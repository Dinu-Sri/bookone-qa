## Required gate evidence

| Gate | Responsible reviewer | Required acceptance evidence |
|---|---|---|
| G-CORE | QA | Original repros plus adjacent invariants pass on the exact candidate; no exposed unresolved P0/P1, unexplained flaky result or missing critical prerequisite. Lower-severity exceptions need named owner decision, affected scope and mitigation. |
| G-PHYSICAL | QA + accounting reviewer | Complete purchase/receipt/bill/payment/sale/return journeys; independently reconciled quantities, costs, cash, AR/AP, tax, journals and dated reports; GRNI, cost methods, partials, locks, roles and failures included. |
| G-SERVICE | QA + accounting reviewer | Service/digital workflows, advances, delivery/recognition, tax, credits and refunds where supported; unsupported advertised functions identified; independently calculated books and real browser outcomes. |
| G-RENTAL | QA + product/accounting reviewer | Booking to return/deposit settlement; availability, timing, damage/loss/repair and overlap controls; quantities, revenue, cash and deposit liabilities reconciled. |
| G-MIXED | QA | Cross-module and company/module-setting transitions, POS where supported, combined documents and historical access; mandatory security/finance combinations beyond pairwise sampling. |
| G-SECURITY | QA + independent security reviewer | Real actor/action positives and denials, tenant/dimension isolation, revoked/stale sessions, database role, file/upload/export boundaries and direct server requests. OWASP ASVS can structure coverage; a mapping or CI pass does not certify compliance. |
| G-ARCHIVE | QA | Real encrypted source-A to new-empty-B data/files journey, remapping, book/stock reconciliation, attachment byte integrity, wrong pair/password and repeat guards. Execute last as requested, but before customer acceptance. |
| G-RECOVERY | Operator + QA | Supported historical upgrade with preserved records, migration failure handling and isolated operator database/object recovery; measured recovery time and recoverable-data age against agreed targets. A tenant archive is separate from operator DR. Never restore production under staging authorization. |
| G-LK | Qualified Sri Lankan accounting/legal reviewers as applicable | Applicable framework/entity/tax/privacy decisions and rulebook RF-01–10 review records; reviewer, date, qualifications, examples and limitations. AI defaults and code behaviour cannot supply expert approval. |
| G-PERFORMANCE | Product owner + QA/operator | Agreed representative company sizes, concurrency, latency/throughput/error thresholds and test duration recorded before execution; isolated load results, retry/interruption tests and resource behaviour meet those thresholds. No shared staging stress without separate authorization. |
| G-OPERATIONS | Operator + QA | Actual deployment/upgrade rehearsal, useful error/availability alerts, log redaction, storage/database failure detection and incident/support procedure. Verify safe release recovery including incompatible schema/data changes, not merely an older image. |
| G-USABILITY | Representative business users + QA | Users independently finish supported daily work and correction/reversal flows, understand totals/errors, and can obtain usable documents/exports on declared browsers/devices; record observed blockers and acceptance. |
| G-RELEASE | Owner with QA/reviewer evidence | Every required gate accepted for one frozen image/source/schema/config/rulebook/QA fingerprint, limitations disclosed, named decision dated. Stale build or an intervening change invalidates approval for the changed candidate. |

These are requirements, not evidence of executed work or booked reviewers. External review, infrastructure and numeric performance/recovery target decisions remain open until recorded. QA can continue independent work while those are pending.

## Evidence record and change control

For each gate record: candidate source SHA and image digest; observed deployment stamp; migration set and upgrade origin; relevant non-secret configuration/role profile; QA SHA/content hash; rule revisions; immutable run IDs; expected versus actual values; passed/failed/blocked/skipped/not-run counts; reviewer/date/decision; unresolved risks and next action. Keep synthetic aliases public and credentials, real identifiers, archives and raw evidence private.

Historical runs remain immutable. Every new code/dependency/schema/config/rule change gets impact review, shared core regression and affected lifecycle/security checks. Unknown impact broadens checks. Tests remain in this QA repository, while the product needs a minimal CI integration that cannot publish a release before the required quality gate. Source discovery and helper tests are separate from deployed business acceptance.

## Pilot and general availability

After the launch-critical gates pass, the owner may authorize a limited supervised pilot with explicit supported businesses, reconciliation schedule, monitoring, support contact, rollback/recovery plan and exit criteria. Pilot-specific data risks and customer expectations must be disclosed. No pilot, customer contact or production onboarding is authorized merely by this plan.

General availability requires the approved scope's gates and pilot acceptance where selected. A scoped pilot cannot silently remove service/digital/rental/mixed from the full objective. Material defects stop expansion and trigger impact assessment and regression. Do not keep adding features to a frozen release candidate without restarting the affected acceptance work.

Reference: [OWASP ASVS](https://owasp.org/projects/asvs) supplies verifiable application-security requirements; this project has not claimed ASVS certification.
