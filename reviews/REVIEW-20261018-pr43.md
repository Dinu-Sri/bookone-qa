## 1. Server-error field loss: cause identified from source and React's contract

The chain is:

1. `createCommercialDocumentFromForm` returns `{ok:false,error}` for ordinary business rejection.
2. `InvoiceDocumentForm` awaits `toastIfFormError(await createCommercialDocumentFromForm(fd))` and resolves normally.
3. `toastIfFormError` displays an error but returns void; it does not make the form action fail or retain submitted values.
4. The invoice's issue/delivery/due dates, notes and payment mode are uncontrolled fields using `defaultValue`. Product lines use React state.

React documents that a successful function action resets uncontrolled fields: [official form reference](https://react.dev/reference/react-dom/components/form), retrieved 18 October 2026. The business operation failed, but the form action fulfilled. That distinction explains why controlled lines survived while dates/notes reset in the live P15-08 observation.

A local diagnostic executed the actual extracted client action wrapper and toast helper with a substituted server returning a synthetic business error: it emitted one toast and resolved `undefined`. This verifies that control-flow link, not the real server/database or a React DOM render. React packages were unavailable in the partial checkout; no isolated React DOM reproduction is claimed. Combined with the documented reset semantics and existing live before/after values, the reset mechanism is identified at source/contract level; a product fix still needs a fresh deployed retest.

**Fix requirements for the coding agent:** make failed submissions retain the entire submitted state. Either control the relevant fields consistently, or explicitly capture/repopulate submitted values through the form-state approach, or manage submission/reset deliberately with a supported event-handler pattern. Simply returning `{ok:false}` from another wrapper, adding a toast, or adding `useActionState` without restoring uncontrolled values is not a demonstrated retention fix. Do not throw routine validation failures into an error boundary that discards the editor.

Preserve submitter intent (draft/post/print), idempotency identity, pending/busy recovery, and successful redirect behavior. Avoid catches that swallow framework redirects or a `finally` reset after an error. Audit shared invoice/quote/sales/purchase forms and nested party/dimension/hire/tax/export inputs. Only delivery/due/notes loss is directly live-reproduced; reset of other uncontrolled fields is an affected-scope concern, not another claimed live finding.

Acceptance requires per-field before/after equality on a real server refusal, unchanged business state, safe correction in the retained form posting once, normal success, and the separate client 150% control. See the existing retention defect and new queue.
